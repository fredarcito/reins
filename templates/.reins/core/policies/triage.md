# Triage policy

Every task gets a level before acting. **reins measures it** from the files you expect to touch; you name the files, not the level. You raise it when you know the task is bigger than its files show, and the person can change it.

A task is anything that needs reading the repo, running a command or changing a file. Information-only messages (a question you can answer from the conversation, a confirmation of the workflow) are not tasks: no level, no announcement, no `triage.log` line. A question whose answer needs repository work is a task: triage it.

| Level | Signal | What you do |
| --- | --- | --- |
| small | A named file or function; a bounded change | Read only that file and its note. Don't explore (`reins scope` and `reins impact` are not exploring). No notebook |
| medium | One domain, several files, no new architecture decisions | Read the module note first (purpose, map, how it works); search the code only for what it does not answer. Summarize in two lines before editing. Mini notebook |
| large | Several domains, a new feature, a refactor, a contract change, a migration, or "review everything" | Write done criteria, run `npx reins impact` on each folder or file the plan changes, use the explorer (read-only; hand it the impact output), present a plan and **wait for confirmation**. Full notebook |

## Rules

- **Explicit override (highest priority):** `[quick]` or `/quick` = small; `[deep]` or `/plan` = large. Don't announce the level then; record it with `npx reins triage <small|large> "<reason>" --override`.
- **Announce:** one line with the level reins measured and the reason, before acting. Small and medium continue without waiting; large presents the plan and waits.
- **Find the area first:** before reading or searching code, run `npx reins triage "<reason>"` with no files, writing the reason with the names the code uses ("add Company filter to JobMatches"). It measures and records nothing: it matches the words against the module notes (names, paths, the folders they cover, their text) and prints the likely areas and their notes. Start exploring from there; the code wins if a note disagrees, and say so. No match → pick the area from the notes index in AGENTS.md (`npx reins notes <folder>`).
- **Measure it:** run `npx reins triage "<reason>" --files <files or folders you expect to touch>`. reins measures the level from them (domains, public APIs, `architecture.yml`, number of code files) and prints it: that is the level you announce. Don't estimate it yourself. **Raise it** when the task is bigger than its files show (a new feature whose files don't exist yet, a refactor, a contract change, a migration): `npx reins triage large "<reason>" --files …`; reins keeps the higher of yours and the measured one, so you can't go below the measure. It also prints the notes of those files you have not received yet. Without `--files` only `large` is recorded, for a task whose files can't be listed ("review everything"). If the level comes out large, present the plan and wait before editing. It appends a line to `.reins/progress/triage.log` with the date, the branch and the commit the task starts from (HEAD). `reins doctor` compares the level with this task's diff: changes since that commit, plus uncommitted ones. Tasks started at the same commit share that diff, so the highest of their levels counts. `reins resume` removes the lines of deleted branches and of tasks whose commits are already in the base branch.
- **When in doubt about the files:** name the folder, not two of its files; and say what could raise the level ("medium, but large if another domain shows up").
- **Objective signals:** `npx reins scope <paths>` prints the domains, notes and minimum level (the same measure `triage --files` records): 1 domain and ≤ 3 files = small; 1 domain and more files = medium; 2+ domains, a public API or `architecture.yml` = large. Docs and tests are not counted (`triage.not_counted` in `.reins/doctor.yml`). For a task about a whole domain or folder, pass the folder, not two of its files.
- **Impact — don't skip it:** run `npx reins impact <file-or-folder>`
  1. when the task restructures, refactors or optimizes a domain or folder: on that folder, while mapping, before the plan;
  2. before editing a file other code may import (a component, util, type, hook, barrel or public API). Unsure whether it's shared → run it: one call is cheaper than a wrong level.

  In Claude Code, opening a shared file whose minimum level is above the declared one (or with no level declared) brings a warning from reins: stop, tell the person, re-triage with `npx reins triage`, and for large present the plan before editing.

  Never conclude "nothing shared changes" without it. It prints the consuming domains, the imports that bypass a public API, the notes to read and the minimum level if the change breaks importers; it is not exploring, so it applies at every level. It sees imports, not HTTP calls: find callers of an API route with grep. For symbol-level questions, grep inside the domains it lists.
- **Escalate mid-task:** `npx reins triage` and every `npx reins progress` edit warn when the task's diff already looks bigger than its level. Tell the person **when it happens**, not in the final summary: say the new level and why, and for large present the plan and wait. Stop and propose a higher level if a second domain appears, the thresholds are exceeded, you need to change a public API, a rule or the baseline, or `reins check` fails for something unexpected. Run `npx reins triage <new level> "<reason>"` again. Don't escalate "just in case".
