# Proposal: one adapter per coding agent (Claude Code, Codex, Cursor)

- **Date:** 2026-11-08
- **Status:** Proposed. Cursor verified on 2026-11-08 (`docs/VERIFIED.md` P12): it runs the Claude Code hooks reins already generates, so Cursor needs small fixes, not an adapter. Codex still unverified.
- **Why now:** the team uses both Codex and Cursor next to Claude Code (stated 2026-11-08). Today only Claude Code gets the hooks that deliver the task notebook, module notes and the impact warning at the right moment; the others only get `AGENTS.md` and `reins doctor` afterwards.

## 1. Principle

reins stays provider-neutral by keeping **all logic in the CLI** and making each provider a **thin, generated adapter**:

- Neutral core (exists): `AGENTS.md` (read by all three) and the `reins` commands: `resume`, `notes`, the impact hint, `triage`, `progress`.
- Adapter per agent: generated by `reins sync`, never edited by hand. It does two things only:
  1. writes that agent's hook configuration, pointing at `reins <command> --hook --agent <name>`;
  2. translates the agent's hook input (JSON payload) and output format (added context, deny with a reason, nothing).

The Claude Code adapter already exists (`.claude/`, optional since 0.8.0 with `--skip-claude`, recorded in `.reins/.generated.json` as `adapters: { claude }`). This proposal generalizes it; it does not change the neutral core.

```
reins sync --agents claude,codex,cursor        (persisted in .reins/.generated.json)

               neutral logic (reins CLI)
      resume · notes · impact hint · triage · progress
                          │
      ┌───────────────────┼───────────────────┐
 claude adapter      codex adapter       cursor adapter
 .claude/settings    .codex/ (config)    .cursor/hooks.json
```

## 2. What reins needs from a hook, and what each agent seems to offer

Unverified for Codex and Cursor: from their docs and third-party guides as of 2026-11-08, which disagree between versions.

| reins moment | Needs | Claude Code | Codex | Cursor |
| --- | --- | --- | --- | --- |
| Session start, `/clear`, compaction → task notebook, other tasks, notes, background impact map | Add context; know the session id and source | ✅ verified (P9, P11) | `SessionStart` with startup/resume/clear/compact/fork and added context (documented) | ? (no session-start event found yet) |
| Read or edit a file → module notes, impact warning | Add context **before** the edit | ✅ verified (P1, phase 6) | `PreToolUse`: deny or rewrite input; added context unclear; older versions only covered shell commands | `beforeReadFile`: allow/deny; added context unclear. `afterFileEdit` is notification-only (too late) |
| Session id for `progress` claims | Env var or payload field | ✅ `CLAUDE_CODE_SESSION_ID` (P11) | ? | ? |
| Install | Project-level config file | `.claude/settings.json` | `config.toml` or `hooks.json`; each new hook must be trusted in `/hooks` | `.cursor/hooks.json`; reports of project hooks failing on Windows |

**Degrading when a capability is missing**, decided per adapter, never in the core:

1. Can add context → same as Claude Code.
2. Can only deny → for the impact warning, deny the first edit of a shared file under a lower declared level, with the warning as the reason (the "stricter" option deferred in DECISIONS, "Impact through the notes hook"). Notes are not worth a deny: skip them.
3. No hook → `AGENTS.md` and `reins doctor`, as today. Session id from `REINS_SESSION` if the agent can set it; otherwise the "no session id" rules of the multi-session notebooks.

## 2b. Cursor result (P12)

Cursor 3.29.9 loads `.claude/settings.json` hooks and honors `additionalContext`, so the existing Claude Code adapter already covers Cursor's session start and file reads/edits. Instead of a Cursor adapter, three small fixes:

1. `sessionId` also reads `CURSOR_CONVERSATION_ID` (the agent's shell has it, equal to the hooks' `session_id`).
2. Hook responses always use Claude's event names (`SessionStart`, `PreToolUse`) instead of echoing `hook_event_name`, which in Cursor is `sessionStart` / `preToolUse`.
3. After a compaction Cursor can't re-deliver context: rely on the `AGENTS.md` line "the conversation was compacted → run `npx reins resume`".

Fixes 1 and 2 were built on 2026-11-08, and reins' real hooks were verified in this repo opened in Cursor (P12). One more fix came out of it: Cursor only fires session start when a native hook defines it, so `sync` writes a no-op `sessionStart` into `.cursor/hooks.json` (with the Claude Code adapter; merged like `.claude/settings.json`). Codex is the only agent left to verify.

## 3. Plan

1. **Verify (no code).** On a machine with current Codex and Cursor: a probe hook that logs its payload and returns context, for each event in section 2. Record the results in `docs/VERIFIED.md` and fill the table. Scripts in `scripts/verify/`, like `cc-session-id.sh`. Also check that Cursor does not already run Claude Code hooks through its "third-party hooks" support, which would make a Cursor adapter partly redundant.
2. **Extract the adapter interface from the Claude Code one**, together with the first new adapter, not before: files to generate, payload in, response out, capabilities. `adapters: { claude, codex, cursor }` in the manifest; `--agents` on `sync`, `install` and `update`; `--skip-claude`/`--claude` keep working.
3. **Codex adapter, then Cursor**, in the order step 1 shows is most useful. `sync --check` and `reins check` integrity cover the new generated files like the Claude ones.

## 4. Out of scope

- Skills and subagents for Codex and Cursor (Claude Code skills and agents are generated today). Separate question once hooks work.
- Any logic that differs per agent. If an agent needs different behavior, it is a capability in the table, not a branch in the core.
- Messaging between agents or sessions.
